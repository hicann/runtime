# Runtime API 模块拆分

以官方对外接口模块为候选范围，追踪到 Runtime 内部 API 大类成员，再按“建框架、切路由、清旧链”分阶段整改。保证每阶段可独立编译、验证和回退，不把结构重构变成功能变更。

## 收集用户选择

开始前确认以下三项；用户已给出时直接复述并继续，只补问缺失且无法从上下文推断的项：

1. **整改模块**：例如 `Event管理`、`Stream管理`、`内存管理`。
2. **对外接口文档**：官方模块页或模块内任一接口页。若给的是叶子接口页，沿父主题/面包屑定位模块并收集该模块接口全集。
3. **整改建议**：用户指定的接口子集、分批方式或暂缓项。未指定时，默认采用三阶段串行方案；允许只做方案分析、只整改部分接口或继续上一批剩余接口。

同时从请求语义判断是“仅分析”还是“实施并上库”。分析请求不得修改代码、推送分支或创建 PR；推送和创建/更新 PR 必须得到用户明确授权。

调用示例：

```text
使用 runtime-api-module-split：模块=Event管理；文档=https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/latest/API/runtimeapi/aclcppdevg_03_0079.html；建议=先拆 IPC Event，按框架、路由、清理三阶段上库，其余接口形成后续清单；给出的网页用作参考，并结合 docs/zh/api_ref/ 下的文档进行对比验证。
```

## 加载参考

- 始终读取 [method.md](references/method.md)，按其中的方法建立接口全集、调用链和依赖边界。
- 模块为 Event，或用户提到 Event 拆分相关 PR 时，读取 [event-batches.md](references/event-batches.md)，并在使用前刷新其中 PR 状态和最新主线接口现状。
- 制定或执行验证时，读取 [risk-and-validation.md](references/risk-and-validation.md)。
- 生成提交、分支或 PR 方案，以及用户明确要求上库时，读取 [submission.md](references/submission.md)。涉及 GitCode PR 时再读取仓库的 `gitcode-pr` Skill；不得自动发布评论、审批或 PR。

## 首次输出固定为四个 PR

用户首次使用本 Skill 分析一个模块时，第一次方案输出必须完整列出以下 4 个 PR，不得只给三阶段代码 PR：

| 顺序 | PR | 范围 |
|---|---|---|
| 1 | 文档 PR | 只包含“输出要求”中的 7 项文档交付件，不包含源代码、CMake 或 UT 改动 |
| 2 | 第一批框架 PR | 为第一批接口新增或扩展 `ApiXxx`/`ApiImplXxx`、Runtime 生命周期、构建接入和直接 UT，不切换 C API |
| 3 | 第一批路由 PR | 只切换第一批接口的 C API 路由，保留主 `Api` 旧链路并验证行为等价 |
| 4 | 第一批清理 PR | 删除第一批接口在主 `Api`、实现、decorator、平台 stub 和旧 UT 中的残留 |

PR2、PR3、PR4 是同一“第一批接口”的三个串行代码阶段，不是三个不同接口批次。首次输出需为每个 PR 给出范围、不包含项、依赖基线、风险、验证计划、分支/提交建议和 PR 描述要点。实际推送或创建 PR 仍需用户明确授权。

## 执行流程

### 1. 锚定模块接口全集

访问用户提供的官方页面，记录模块名、实际版本、canonical URL 和检查日期。提取模块目录下所有对外接口，不能只按函数名关键词猜测范围。

若仓库已有 `docs/zh/api_ref/` 合并文档，用它校验接口清单和约束，但仍以用户给定的官方模块口径为边界来源。

### 2. 建立端到端映射

逐接口追踪：

```text
官方 acl/aclrt 接口
  -> ACL 实现与 rt/rts 调用
  -> src/runtime/api/api_c*.cc C 入口
  -> 当前 Api 大类及成员函数
  -> ApiImpl/平台实现/对象实现
  -> CMake、stub、UT
```

输出接口映射表，至少包含：对外接口、rt/rts 入口、C API 文件、当前 API 大类/成员、实现位置、平台差异、关键依赖、当前批次决策。

不要假设“一个官方模块等于一个内部 API 类”。一个模块可对应多个 API 大类或多个成员分组；一个内部成员也可能被其他模块复用。

### 3. 划定当前批次

批次排序遵循“先独立、后耦合”原则。先从候选成员中筛出 API 模块边界独立、能够单独完成编译和验证闭环的成员，将职责内聚的成员归入最早批次；再按耦合强度安排后续批次。不要先按接口数量平均分组，也不要为了清空主 `Api` 把跨模块成员提前迁移。

判断成员是否独立时，区分两类依赖：

- **Runtime 基础设施依赖**：通过稳定公开边界使用 Context、Device、Driver、目标资源对象或全局容器。只要不要求另一个业务 API 大类实例存在，且产品构建和失败语义可独立验证，不自动视为跨模块耦合。
- **业务 API 模块依赖**：调用 `ApiXxx`、`Runtime::ApiXxx_()`、主 `ApiImpl` 私有 helper，或把 Stream、Graph capture、Soma 等其他模块的成功后副作用纳入本成员语义。此类成员不得归入独立批次。

在 Runtime 中增加转发函数、移动 include 或只通过公开虚接口调用，只能降低代码层依赖，不能消除业务语义和能力依赖。例如 `ApiEvent` 经 Runtime 转调 `ApiSoma`，仍意味着启用 Event 同步必须同时初始化并支持 Soma，不能据此判定 Event 同步已经独立。

独立批次的成员必须同时满足：

1. 不调用其他业务 API 大类，也不依赖其初始化、析构或可选能力；
2. 不依赖主 `ApiImpl` 中属于其他模块的私有 helper；
3. 参数校验、profiling、成功后副作用、错误码和平台行为可在目标模块内完整保持；
4. 正式产品、tiny/arch5162、910B 和相关 UT 能在不迁移其他业务模块的情况下编译、链接和验证；
5. 同批成员具有一致的资源所有权和相近的验证边界。若不满足内聚性，即使都独立，也应说明原因并分批。

所有独立成员确定后，再逐项记录其余成员的耦合对象、现有调用点、暂缓原因和解除耦合的前置条件。前置条件未完成时保留在原 API 大类，不用 Runtime 包装或双向调用掩盖依赖。

将接口分为：

- **本批整改**：优先选择模块归属明确、无其他业务 API 模块依赖、可独立编译验证并证明行为等价的成员。
- **后续整改**：属于同一官方模块，但仍有平台、内部调用方或跨模块语义依赖；列明前置条件后再推进。
- **暂缓整改**：与其他模块存在强依赖，拆出会同时扩大多个模块边界。
- **无需整改**：已在目标模块链路、仅为 ACL 包装，或不满足拆分收益。

必须输出未纳入接口及原因。部分接口完成拆分时，只能表述为“完成本批接口”，不能表述为“完成整个模块”。Event 管理应分别报告已合入批次、待合入批次和仍待分析批次，不能将其中任一子集视为模块全部完成。

### 4. 固化行为等价契约

在改代码前对每个本批接口记录：

- C API 签名、handle 包装/解包和参数透传；
- 参数校验顺序、返回码、错误日志和 feature-not-support 语义；
- profiling begin/end、线程环境标志和隐式 Context/Device 行为；
- 对象创建、失败回收、销毁和 Runtime 初始化回滚；
- v100/v200/v201、cmodel、tiny、arch5162、910B 等产品/UT 构建差异；
- 对外 ABI、内部虚函数布局和 Runtime 成员布局风险。

将这些项作为三阶段共同的验收基线。

### 5. 生成三阶段方案

默认按以下串行边界拆分；公共能力仅在确有缺口时先独立整改：

1. **框架阶段**：新增 `ApiXxx`、`ApiImplXxx`、创建器、Runtime 生命周期、产品 CMake/stub 和直接 UT；不切换现有 C API 路由。检视触发的窄范围头文件/依赖清理可在本阶段合入后单独补充，但不算新的业务阶段。
2. **路由阶段**：只把本批 C API 入口切到 `ApiXxx`，保留主 `Api` 旧方法；增加路由证明和新旧行为等价 UT，不做旧链路删除。
3. **清理阶段**：在新路由验证通过后，删除主 `Api`、`ApiImpl`、decorator、平台 stub 和旧 UT 中的残留；完成全矩阵验证。初始分析与方案文档由独立文档 PR 承载，不混入代码 PR。

每阶段列出：依赖基线、包含项、不包含项、风险点、最小验证、补充验证、建议分支名和提交标题。

### 6. 实施与复核

仅在用户要求实施时修改代码。每完成一个阶段：

1. 对照映射表确认没有混入下一阶段接口。
2. 对照行为等价契约检查成功和失败路径。
3. 按风险矩阵执行定向 UT、多产品编译/链接和静态检查。
4. 更新当前批次与剩余接口清单。
5. 先本地汇报差异和验证证据；用户明确要求后再推送或创建 PR。
6. 代码发生变更后刷新已有 PR 时，必须同步更新线上 PR 描述中的变更范围、风险、实际验证结果和剩余工作，并回读确认描述与最新代码一致。
7. PR 提交后必须跟踪线上 CI；文档 PR 的适用检查以及三个代码 PR 的 CI 编译任务必须通过。CI 未执行、失败或证据不可读时，不得宣称该 PR 验证完成。

## 输出要求

以下 7 项是首次输出中 PR1 的文档交付件。它们必须进入独立文档 PR，不得与第一批代码改动放在同一个 PR：

1. 模块、官方文档版本和接口全集。
2. 对外接口到内部 API 大类成员的映射表。
3. 本批、后续、暂缓和无需整改清单。
4. 三阶段 PR 方案及每阶段风险/验证矩阵。
5. 上库顺序、分支/提交建议和按仓库模板生成的 PR 描述。
6. “本批完成后仍未拆分的模块接口”清单，避免形成模块已全部整改的误解。
7. 已完成、进行中和后续批次状态，以及下一步的依赖基线和执行顺序。

除上述文档交付件外，首次输出还必须给出 PR2、PR3、PR4 的完整三阶段代码方案。四个 PR 创建后均要报告线上 CI 状态；三个代码 PR 必须以 CI 编译通过作为可合入条件。
