# 可选组件隔离方法

## 1. 判断是否适合隔离

先证明目标产品确实不需要该组件：

- 公开文档和产品能力表标明不支持，或产品 owner 明确确认不使用。
- 目标产品 C API 可统一返回既有 feature-not-support 错误码。
- 目标产品内部没有初始化、静态注册、回调、析构或间接调用依赖该组件。
- 保留公开符号不会要求链接具体实现。

若只是当前测试未覆盖，不能据此裁剪。若其他组件复用其核心状态或生命周期，先拆公共能力。

## 2. 建立四张表

### 2.1 调用链表

| 公开接口 | C 入口 | 抽象接口 | 具体实现 | provider/driver | 目标产品行为 |
|---|---|---|---|---|---|

同时记录参数检查、错误转换、日志、profiling、Context/Device 隐式行为和对象生命周期。

### 2.2 源文件矩阵

| 源文件/能力 | 普通产品 | 目标产品 | 普通 UT | 目标 UT | 处理决定 |
|---|---|---|---|---|---|

检查 `src/runtime/cmake/*.cmake` 和所有平台 `CMakeLists.txt`。新增或移动一个
`.cc` 时，不仅搜索正式目标，也搜索静态 UT 源列表和 910B、tiny、
cmodel/camodel、arch5162 等单独目标。

### 2.3 具体类型依赖表

搜索以下依赖：

```bash
rg -n \
  -e 'ApiImplXxx|CreateImplXxx|IsImplXxxSupported' \
  -e 'sizeof\(ApiImplXxx\)|api_impl_xxx.hpp' \
  src tests
```

分类记录：

- 需要完整类型的 `new`、`delete`、`sizeof`、成员访问和模板实例化；
- 仅需前置声明的指针、引用和抽象接口；
- 工厂、静态注册、单例和跨 SO 符号；
- 析构、初始化失败回滚和进程退出路径。

公共 Runtime 只保留抽象依赖。具体分配、对象大小和具体日志归属组件实现编译单元。

### 2.4 符号表

从裁剪前普通/目标库提取真实导出集合，不按单一名称前缀猜测。例如 Mbuf 除 15 个 `rtMbuf*` 外还有 `rtBuffGet` 和 `rtBuffPut`。

记录符号名、类型、可见性、定义文件和裁剪后提供者。内部 C++ 方法声明不等同于公开 ABI。

## 3. 设计第一步：自适应准备

第一步解决“无法按编译单元裁剪”的模块特有障碍。按以下顺序选择：

1. **无需修改**：C API、实现和 provider 已各自在专属源文件，依赖闭合。
2. **原样拆源文件**：目标方法混在共享 `.cc` 中，且能按职责完整移动。
3. **提取公共基础能力**：共享 `.cc` 中存在其他模块真实复用的代码，只拆组件私有部分。
4. **收敛静态注册/全局状态**：组件由注册器或全局对象隐式拉入时，先建立可选注册边界。
5. **拆分 API 入口文件**：目标产品需要保留少量 ABI 桩，而通用入口和具体实现耦合时，先划分平台入口。

第一步不得改变调用链和产品支持。Mbuf 的具体方法是把 `NpuDriver::Mbuf*` 从
`npu_driver_queue.cc` 移到 `npu_driver_mbuf.cc`，并让所有原 target 同时编译新文件。
其他组件要重新分析，不能因为存在混合文件就自动照搬。

## 4. 设计第二步：工厂解耦

采用如下边界：

```text
runtime.cc
  -> IsImplXxxSupported()
  -> CreateImplXxxAndGet() : ApiXxx*

api_impl_xxx.cc
  -> include api_impl_xxx.hpp
  -> new (std::nothrow) ApiImplXxx
  -> sizeof(ApiImplXxx)
  -> 分配失败与大小日志
```

本阶段所有平台保持支持，避免将结构重构与能力变化放在同一 PR。工厂返回空时，Runtime 只传播统一初始化错误；具体日志由知道完整类型的工厂负责。

不要把 `ApiXxx::Instance()` 随意移动到实现编译单元。先确认哪个动态库直接调用并提供该符号，避免 API 动态库依赖实现动态库中的新符号。

## 5. 设计第三步：平台隔离

目标平台提供：

- `IsImplXxxSupported() == false`；
- 必要时提供返回空的工厂定义，满足统一声明；
- 对外 C API 不支持桩，保留原签名和 `VISIBILITY_DEFAULT`；
- 每个公开接口的 not-support UT。

目标 CMake 同时移除：通用 C API 文件、具体实现文件、专属 provider 文件。正式 target 与平台 UT target 必须一致。

支持产品继续使用原链路，不应经过平台不支持桩。

## 6. C++ 声明与链接判断

类头文件可以保留未在目标产品中定义的成员函数声明，只要目标链接中没有对这些函数的实际引用。`-Wl,--no-undefined` 检查链接输入中的未解析引用，不要求每个未使用声明都有定义。

以下情况会形成实际依赖：

- 直接或间接调用函数；
- 虚函数被纳入目标所需 vtable；
- 取函数地址；
- 显式模板实例化或静态注册引用；
- 析构或初始化路径调用；
- 链接脚本或 `--whole-archive` 强制拉入含引用对象。

因此必须结合 `nm -C`、`readelf`、`link.txt`、对象列表和最终 `ldd -r` 判断，不能只看源码搜索结果。

## 7. 常见错误

- 只加 `-ffunction-sections/-Wl,--gc-sections`，但组件源文件仍编译且静态初始化仍存在。
- 从 CMake 移除实现文件，却遗漏 Runtime 中的 `sizeof` 或失败日志。
- 删除目标产品 C API 文件后未补 ABI 桩。
- 只按 `rtXxx` 前缀统计符号，漏掉历史命名接口。
- 只修改正式 CMake，遗漏 UT 静态源列表或平台目标。
- 将第一步固定成拆 driver 文件，导致其他组件产生没有收益的机械重构。
- 用不同构建类型或不同 strip 状态比较动态库大小。
