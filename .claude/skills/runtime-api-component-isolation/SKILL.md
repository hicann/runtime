# Runtime API 可选组件隔离

将“不支持某组件”落实为源文件不进入目标产品，而不只是依赖链接器回收未使用函数。保持支持该组件的产品行为不变，并把方案拆成可验证、可回退的阶段。

## 确认输入

开始前确认以下信息；能从代码和构建配置中确定时直接继续：

1. **目标组件**：例如 `ApiImplMbuf`、对应 C API、driver/provider 实现。
2. **目标产品**：例如 arch5162 及其正式库、UT target 和平台实现文件。
3. **兼容要求**：公开符号是否必须保留，不支持时应返回哪个错误码。
4. **裁剪目标**：停止编译的源文件、期望减少的动态库，或明确的大小限制。
5. **交付范围**：仅分析，还是实施、提交 PR 并跟踪 CI。

若组件仍混在主 `Api/ApiImpl` 大类中、尚未形成可独立创建的
`ApiXxx/ApiImplXxx`，先完成模块边界拆分；仓库中存在
`$runtime-api-module-split` 时按其方法执行，再使用本 Skill 做产品级编译隔离。

## 基本约束

1. 支持该组件的产品保持原调用链、参数、错误码、日志和对象生命周期。
2. 目标产品不编译组件实现时，公开 C API 符号集合必须与裁剪前一致；不支持语义由平台 API 桩明确提供。
3. 公共 `runtime.cc` 不包含可选组件具体头文件，不执行其 `new`、`sizeof` 或具体类型日志。
4. 平台差异优先收敛到 CMake 源列表、平台工厂和平台 API 文件；不要在公共源码新增产品宏。
5. 不以“头文件中只有声明”推断可链接，也不以 `--gc-sections` 推断完成隔离；必须检查最终引用、目标文件和动态符号。
6. 动态库大小必须在同一提交基线、编译器、构建类型、链接参数和 strip 状态下对比。

## 执行流程

### 1. 建立边界和基线

逐层追踪：

```text
公开 acl/rt/rts API
  -> api_c*.cc C 入口
  -> ApiXxx::Instance / Runtime::ApiXxx_
  -> ApiImplXxx
  -> driver/provider
  -> 产品 CMake、UT CMake、stub 和导出符号
```

输出源文件矩阵、符号基线、Runtime 生命周期和实际引用证据。不要只搜索类名；同时检查 include、`sizeof`、工厂、虚析构、静态对象、源文件列表和链接输入。

### 2. 选择第一步：自适应准备

第一步的目标是让组件形成可单独加入或移除的编译单元，具体动作必须按模块特性决定，不能机械复制 Mbuf：

- 实现混在共享源文件中：将目标组件方法原样移动到专属源文件，并同步所有正式/UT target。
- C API、具体实现或 provider 已有专属文件：可不拆文件，改为收敛传递 include、静态注册或跨组件辅助依赖。
- 多个组件共享必要实现：先提取真正公共的小型基础能力，不得把无关组件一起标成可选。
- 已经满足编译单元闭合：记录证据并跳过代码 PR，不创建空的第一步 PR。

`ApiImplMbuf` 的第一步采用 PR4264：把 Mbuf driver 方法从
`npu_driver_queue.cc` 原样拆到 `npu_driver_mbuf.cc`。该做法是 Mbuf 案例，
不是其他模块的固定模板。

第一步必须保持所有产品能力不变。若产生代码 PR，应可独立编译和回退；它是否与第二步存在技术依赖，需要根据当前组件明确说明。

### 3. 执行第二步：公共层与具体实现解耦

该步骤是通用稳定模式：

1. 提供抽象工厂和能力入口，例如 `CreateImplXxxAndGet()`、`IsImplXxxSupported()`。
2. 将具体类型分配、`sizeof(ApiImplXxx)`、分配失败日志和大小日志移动到组件实现编译单元。
3. `runtime.cc` 只依赖抽象类型和工厂契约。
4. 本阶段所有原支持平台仍返回支持并创建原实现，不做目标产品裁剪。
5. 增加工厂分配失败和 Runtime 初始化失败传播 UT。

第二步必须是行为保持型重构。对 Mbuf，它对应 PR4265，并且与 PR4264 可独立合入；其他模块必须重新判断，不能直接继承这一独立性结论。

### 4. 执行第三步：目标产品隔离

该步骤同样采用通用稳定模式，并依赖第二步以及必要的第一步准备：

1. 目标平台能力入口返回不支持，组件实现指针保持为空。
2. 从目标产品正式库和 UT target 中移除 C API 通用实现、具体实现和专属 provider 源文件。
3. 在目标平台 API 文件中保留所有公开 C API 符号，签名和可见性不变，统一返回约定的不支持错误码。
4. 为每个公开接口增加目标平台 UT；同时保留支持平台正常路径 UT。
5. 检查目标链接输入不含组件对象、`ldd -r` 无未定义符号、动态符号集合无缺失。

Mbuf 的第三步对应 PR4254。在前两步未合入时，允许用聚合分支验证最终状态；
正式分步骤上库时，第三步必须在前置 PR 实际合入后重放到最新主线并重新执行 CI。

### 5. 验证和上库

按参考矩阵验证支持产品、目标产品、普通/平台 UT、符号、链接、覆盖率和同基线大小。每次代码变化后同步更新线上 PR 描述并回读确认。

CI 必须检查具体任务表。`UT_Test_camodel_check`、覆盖率报告或其他任务失败时进入对应流水线读取日志，修复后重新触发；任务未执行、仍在运行或日志不可读时不得宣称通过。

## 输出要求

每次分析至少输出：

1. 组件端到端调用链和公开符号基线。
2. 正式产品与 UT 的源文件矩阵。
3. 第一步采用、变更或跳过的理由；不得默认套用 PR4264。
4. 第二步工厂解耦方案和第三步目标隔离方案。
5. 每步的依赖、包含项、不包含项、风险、验证、回退和建议提交。
6. 支持产品行为等价证据、目标产品 ABI/不支持语义证据。
7. 同基线动态库大小变化，以及本地和线上 CI 的实际状态。

仅在用户明确要求实施时修改代码；仅在用户明确授权后推送或创建/更新 PR。不得自动发布评论、审批或 slash 命令。
