# 图灵解决方案平台开发部 Agent Skill 开发规范 V1.0

## 1 概述

### 1.1 目的和适用范围

本规范用于统一图灵解决方案平台开发部通用 Agent Skill 的设计、编写、测试、评审、发布和维护要求，直接规范 Agent Skill 交付物及其开发、评审和维护活动，主要面向 Skill 开发者和维护者。

跨组件通用且可以统一执行的要求纳入本规范；只适用于特定仓库的要求，例如具体模块使用的 Skill 名称前缀、工具命令、文件格式和业务流程，由组件内部规范规定。

组件规范可以补充组件特有要求，并通过规则编号引用本规范中的公共规则，不得复制公共规则后独立修改。

### 1.2 Skill 归属和维护位置

创建 Skill 前必须先判断归属：

| Skill 类型                           | 正式维护位置        | 适用规范   |
| ---------------------------------- | ------------- | ------ |
| 跨仓复用、不依赖单个组件内部实现的通用 Skill          | `cannbot` 代码仓 | 本规范    |
| 只服务单个组件，或依赖组件内部代码、流程和环境的组件独有 Skill | 对应组件代码仓       | 组件内部规范 |

通用 Skill 不在组件仓重复维护正式版本；组件独有 Skill 不因本规范强制迁入 `cannbot`。组件仓需要使用通用 Skill 时，只安装或引用 `cannbot` 中的正式版本。无法判断归属时，先由人工评审明确维护仓和责任人，再开始开发。

### 1.3 规则级别和例外

第二章及后续章节的规则使用以下两个级别：

| 级别 | 含义 |
| --- | --- |
| 要求 | 准入条件，不满足不得合入或发布 |
| 建议 | 默认做法；不采用时，在评审材料中说明原因和替代措施 |

规则适用性和级别可以根据具体场景和风险在评审中确定。把“要求”降为“建议”时，必须记录规则编号、适用范围、调整理由、影响和评审结论。

### 1.4 规范冲突

通用 Skill 先遵守 `cannbot` 仓的安全、兼容性和贡献规范，再依次遵守本规范、Agent Skills 开放规范和目标 Agent 平台官方规范。组件独有 Skill 先遵守组件仓的安全、兼容性、贡献规范和组件内部规范，再遵守开放格式要求。

本规范不替代组件内部规范，组件内部规范也不改变 `cannbot` 通用 Skill 的合入条件。发生冲突时，评审材料必须记录冲突来源、适用范围和处理结果。

### 1.5 Skill 内容组织

Skill 内容分为三层：

1. **发现层**：`name` 和 `description`，用于判断是否调用 Skill；
2. **执行层**：`SKILL.md` 正文，即 YAML frontmatter 结束后的 Markdown 内容，用于保存核心流程、边界、判断条件和完成标准；
3. **资源层**：`references/`、`scripts/` 和 `assets/`，按任务需要读取或执行。

调用条件集中写在 `description`，详细步骤写在 `SKILL.md` 正文，条件性资料和确定性操作按用途拆到资源目录。后续章节分别规定三层内容的具体要求。

### 1.6 规则编号

规则编号采用 `G.<Element>.<Number>`：

- `G` 是 Guideline 的首字母，表示规则；
- `Element` 是规则所属类别的三位英文字母缩写，具体取值及含义见下表；
- `Number` 是规则在所属类别内的序号，从 1 开始递增，使用两位阿拉伯数字，不足两位时高位补 0。例如，创建条件类别的第一条规则编号为 `G.CRE.01`。

同一条款只在一个章节中定义，其他章节通过编号引用，不复制条款内容。每条规则必须明确责任主体或规范对象，并能独立说明谁在什么阶段执行什么要求；引用其他规则时，本条仍须保留完整的核心要求。

| 类别 | 内容 |
| --- | --- |
| `CRE` (Creation) | 创建条件、任务边界、输入和输出 |
| `STR` (Structure) | 目录、文件和链接 |
| `MET` (Metadata) | 命名、frontmatter 和调用条件 |
| `BOD` (Body) | `SKILL.md` 正文和执行流程 |
| `RES` (Resources) | references、assets 和依赖 |
| `SCR` (Scripts) | scripts、参数、输出和测试 |
| `SRC` (Sources) | 信息来源和维护 |
| `SEC` (Security) | 安全、权限和数据 |
| `EVL` (Evaluation) | 评测、测试和指标 |
| `REL` (Release) | 开发、变更回归和发布 |
| `MNT` (Maintenance) | 维护、版本和停用 |

## 2 Skill 创建条件和任务边界

### 2.1 创建条件

#### G.CRE.01 创建前先证明真实能力缺口

**【级别】** 要求

**【描述】**

新增 Skill 前，使用真实任务记录证明 Agent 反复出现错误、遗漏、不必要追问或结果不一致。没有可复现的能力缺口，不应新增 Skill。

每个 Skill 都会增加调用冲突和加载成本。不能仅因为某段说明可以写成 Skill 就创建 Skill。

#### G.CRE.02 优先选择合适的承载位置

**【级别】** 要求

**【描述】**

创建 Skill 前，根据内容的生效范围和使用方式确定是否由 Skill 承载：

| 内容 | 放置位置 |
| --- | --- |
| 全仓始终生效的短规则 | `AGENTS.md` |
| 供人阅读的稳定规范 | `docs/` 或仓库正式文档 |
| 特定用户意图下的多步流程 | Skill |
| 实时外部系统能力 | MCP、CLI 或 API |
| 多角色、长状态的复杂编排 | Agent、workflow 或 plugin |

确定由 Skill 承载后，根据内容用途选择对应的文件或目录：

| Skill 内容 | 文件或目录 |
| --- | --- |
| 名称、调用条件、核心流程、任务边界和完成条件 | `SKILL.md` |
| 仅在特定条件下读取的详细资料 | `references/`，具体要求见 `G.RES.01` 至 `G.RES.03` |
| 确定性、重复性操作 | `scripts/`，具体要求见 `G.SCR.01` 至 `G.SCR.05` |
| 输出时复制或加工的静态文件 | `assets/`，具体要求见 `G.RES.04` |
| 评测用例 | `evals/`，创建条件见 `G.EVL.01` |
| 平台适配配置 | `agents/`，具体要求见 `G.MET.05` |

只创建任务实际需要的目录，目录结构按 `G.STR.03` 执行。

### 2.2 任务边界

#### G.CRE.03 一个 Skill 只处理一个主要用户意图

**【级别】** 要求

**【描述】**

一个 Skill 可以覆盖同一用户意图下的设计、执行和验证步骤，但不得混入互不相关的任务。多个独立意图应拆分为可组合的 Skill，或交给 workflow 编排。

#### G.CRE.04 明确不同任务的操作边界

**【级别】** 要求

**【描述】**

`SKILL.md` 正文根据任务类型明确交付边界，并按 `G.SEC.01` 规定默认权限：

- 诊断类 Skill：用户只要求根因时，不执行修复；
- 代码检视类 Skill：只报告证据、影响和建议，不默认修改文件；
- 测试类 Skill：只修复本次测试范围内的问题，并区分产品缺陷与测试缺陷；
- 开发类 Skill：完成实现并执行与修改范围对应的构建、测试和检查，不能以“代码已生成”作为完成。

#### G.CRE.05 写清负责范围和相邻边界

**【级别】** 要求

**【描述】**

`SKILL.md` 正文写清负责的任务、不负责的任务，以及与相邻 Skill 的分工，并规定 Agent 对超出职责边界的请求不得变更任务目标或执行其他任务；无法依据现有信息唯一选择时，只询问会改变处理结果的关键问题。

创建或修改 Skill 时，只检查可能处理同一用户请求的已注册 Skill。符合以下任一条件的，可以判定为相邻 Skill：

- 属于同一领域或模块；
- 处理相同或相近的任务对象；
- 接收相同类型的输入或产生相同类型的输出；
- `description` 中的调用场景或用户表达存在重叠。

应先通过 Skill 索引以及仓库内的 `name`、`description` 检索候选项，不要求逐个分析全部 Skill。发现相邻 Skill 时，写清职责分工，并通过负向用例验证调用边界；未发现候选项时，不需要虚构相邻 Skill。

### 2.3 输入、输出和完成条件

#### G.CRE.06 定义输出、停止条件和完成标准

**【级别】** 要求

**【描述】**

`SKILL.md` 正文说明输出内容；生成文件时说明保存位置；同时说明完成前需要执行的构建、测试或检查，以及无法继续时的停止条件和失败输出。完成条件定义为：用户任务实际完成，并通过与任务范围对应的构建、测试和检查；不得将“已输出报告”或“已生成代码”直接定义为完成。

## 3 目录和文件

### 3.1 标准目录

#### G.STR.01 Skill 只维护一个正式版本

**【级别】** 要求

**【描述】**

通用 Skill 的正式版本维护在 `cannbot` 代码仓的 `.agents/skills/<skill-name>/`，组件独有 Skill 的正式版本维护在对应组件仓的 `.agents/skills/<skill-name>/`。同一 Skill 只能有一个正式维护位置。`.claude/skills/` 等平台目录只能保存自动生成的副本、经过验证的链接或只包含平台差异的适配文件，不得人工复制完整的 `SKILL.md` 正文后分别修改。

#### G.STR.02 使用规定的入口文件和非空 `SKILL.md` 正文

**【级别】** 要求

**【描述】**

每个 Skill 根目录包含大小写完全一致的 `SKILL.md`。文件以可解析的 YAML frontmatter 开头，`SKILL.md` 正文非空。

#### G.STR.03 只创建实际使用的目录

**【级别】** 要求

**【描述】**

标准 Skill 可按需包含以下目录：

```text
<skill-name>/
├── SKILL.md
├── references/          # 可选：Agent 按条件读取的资料
├── scripts/             # 可选：可执行脚本
├── assets/              # 可选：输出静态资源
├── evals/               # 按 G.EVL.01 创建：该 Skill 的评测用例
└── agents/              # 可选：平台适配配置
```

可选目录存在时不得为空，不提交 `.gitkeep` 等占位文件。目录名使用复数形式，不得创建 `reference/`、`script/` 或 `asset/`。

`evals/` 的创建条件和最低用例要求按 `G.EVL.01` 执行。

#### G.STR.04 禁止 Skill 内新增额外说明文档

**【级别】** 要求

**【描述】**

Skill 内不得单独新增 `README.md`、`CHANGELOG.md`、安装手册或速查手册。Skill 的使用说明写入 `SKILL.md` 或 `references/`；变更历史由 Git 或仓库发布系统维护。

### 3.2 文件和链接

#### G.STR.05 使用相对路径并保证链接有效

**【级别】** 要求

**【描述】**

Skill 内链接从 Skill 根目录使用相对路径和正斜杠。相对链接指向已提交文件；外部链接对目标用户和执行环境可访问。

#### G.STR.06 统一文本编码并清理无关文件

**【级别】** 要求

**【描述】**

Skill 内文本文件使用 UTF-8，换行符和脚本执行权限遵守所在仓库规则。不得提交编辑器备份、构建结果、运行状态、临时文件或未替换的模板占位符。

文档中允许使用已经定义的参数占位符，如 `{model_name}`；占位符在同页说明含义。

#### G.STR.07 检查显式依赖和引用同步

**【级别】** 要求

**【描述】**

声明显式 Skill、Agent 或工作流依赖时，检查依赖对象存在且依赖图无环。普通 Skill 没有依赖字段时，不得为了检查而新增平台专有字段。

增删 Skill 或修改 Skill 名称后，同步更新索引、依赖、平台配置、脚本路径和相关 Agent 名。

## 4 命名、元数据和调用条件

### 4.1 Skill 命名

#### G.MET.01 使用合法且可识别的 Skill 名称

**【级别】** 要求

**【描述】**

`name` 满足以下条件：

- 长度不超过 64 个字符；
- 只包含小写英文字母、数字和连字符；
- 不以连字符开头或结尾，不含连续连字符；
- 与 Skill 目录名逐字符一致；
- 在仓内全局唯一（自动生成的兼容副本不重复计数）。

#### G.MET.02 模块强相关 Skill 使用唯一模块前缀

**【级别】** 要求

**【描述】**

全局通用 Skill 和仓内通用 Skill 不强制添加模块前缀。与具体模块实现、接口或流程强相关的 Skill 采用“模块前缀 + 行为或对象”的名称。组件规范为每个模块定义唯一前缀。

#### G.MET.03 避免模糊名称

**【级别】** 建议

**【描述】**

Skill 名称应说明具体能力，建议采用“领域 + 动作或对象”的形式。名称应避免 `helper`、`tools`、`common` 等模糊词，也不应只使用内部类名或目录名。

### 4.2 `frontmatter` 字段

#### G.MET.04 使用可解析的标准 frontmatter

**【级别】** 要求

**【描述】**

`SKILL.md` 以 `---` 包裹的 YAML frontmatter 开头。公共 Skill 显式声明 `name` 和 `description`。

frontmatter 支持以下字段：

| 字段              | 必需  | 约束                                                           |
| --------------- | --- | ------------------------------------------------------------ |
| `name`          | 是   | 长度不超过 64 个字符，只使用小写字母、数字和连字符，并与 Skill 目录名完全一致。详细要求见 `G.MET.01`。 |
| `description`   | 是   | 长度不超过 1024 个字符，说明 Skill 的功能和调用条件。详细要求见 `G.MET.06`。             |
| `license`       | 否   | 使用简短的许可证名称，或引用 Skill 目录内的许可证文件。                              |
| `compatibility` | 否   | 长度不超过 500 个字符，仅在 Skill 对目标产品、系统软件包、网络访问或运行环境有明确要求时填写。          |
| `metadata`      | 否   | 键和值均为字符串，用于记录标准字段未覆盖的附加属性；不要求包含 `version`。                   |

`license`、`compatibility` 和 `metadata` 是可选的说明性字段。Skill 不得依赖目标平台对这些字段的解析结果控制调用、权限或执行流程。

```yaml
---
name: ascendc-kernel-reviewer
description: 审查 Ascend C Kernel 的正确性和性能。当用户提交 Kernel 源码，或要求分析内存搬运、Tiling 切分、流水并行和性能报告时使用。
license: Apache-2.0
compatibility: 需要 CANN 工具链和 Ascend NPU 运行环境
metadata:
  owner: npu-infra
---
```

确需新增公共 frontmatter 字段时，先在 `cannbot` 规范中定义字段名称、类型、是否必填、默认值和兼容行为，并增加相应的解析和校验测试。规范和校验器尚未支持的字段，不得写入公共 `SKILL.md`。

#### G.MET.05 隔离平台专有字段

**【级别】** 要求

**【描述】**

只影响特定平台的调用参数、工具权限、界面展示和执行策略写入对应平台的适配文件，不得写入公共 `SKILL.md`。平台适配文件不得改变 Skill 的任务范围、调用条件、权限边界和完成标准。

例如，`allowed-tools` 仅由部分平台支持，属于平台专有字段。需要配置工具权限时，将该配置写入目标平台的适配文件。

### 4.3 `description` 编写

#### G.MET.06 `description` 写清核心任务、代表性触发场景和关键边界

**【级别】** 要求

**【描述】**

`description` 是调用规则，不是宣传语或 `SKILL.md` 正文摘要。内容简洁说明 Skill 的核心任务和输出、代表性的用户触发场景，以及最容易与其他 Skill 混淆的关键边界。

不得在 `description` 中穷举所有用户表达、不适用场景或异常分支。完整职责边界和已知限制写入 `SKILL.md` 正文；更多正向和负向表达及其预期结果维护在 `evals/` 中。

关键意图应放在前部，`description` 的长度不得超过 1024 个字符。

#### G.MET.07 `description` 与 `SKILL.md` 正文使用一致术语

**【级别】** 要求

**【描述】**

`description` 中的任务名称、对象名称和边界术语与 `SKILL.md` 正文一致，同一概念不得使用多个名称。

#### G.MET.08 用正向和负向用例维护调用边界

**【级别】** 要求

**【描述】**

新增或修改 `description` 时，重新生成该 Skill 的正向用例和负向用例。

## 5 `SKILL.md` 正文和执行流程

### 5.1 `SKILL.md` 正文内容

#### G.BOD.01 `SKILL.md` 正文只写任务所需的核心信息

**【级别】** 要求

**【描述】**

`SKILL.md` 正文使用直接、可执行的语句，重点说明领域规则、判断条件、执行流程和容易遗漏的情况。不得讲解 Git、编程语言、Markdown 或 shell 等通用基础知识，也不得用“你是某领域顶级专家”等角色描述代替具体规则。

#### G.BOD.02 `SKILL.md` 正文必须包含完整任务信息

**【级别】** 要求

**【描述】**

`SKILL.md` 正文不强制套用固定标题，按适用范围包含以下内容：

- 必需输入和前置条件；
- 采用的信息来源；
- 工作步骤；
- 判断条件、分支和例外；
- 输出、停止条件和完成检查；
- 已知限制和常见错误；
- 按需读取或执行的资源。

不得为不适用的内容创建空章节。

### 5.2 步骤、分支和异常

#### G.BOD.03 每个关键步骤写清输入、动作、判断标准和输出

**【级别】** 要求

**【描述】**

`SKILL.md` 正文中的每个关键步骤说明：使用什么输入、执行什么动作、依据什么标准判断、产生什么输出。复杂规则应提供最小命令、输入片段或输出片段，使结果可以对照检查。

### 5.3 参数

#### G.BOD.04 参数说明使用自然语言，不依赖特定平台

**【级别】** 要求

**【描述】**

`SKILL.md` 正文使用自然语言说明如何识别参数，不得直接依赖 `$0`、`$ARGUMENTS` 等宿主占位符。平台适配文件负责将平台显式参数转换为所需输入。

### 5.4 规模和按需加载

#### G.BOD.05 控制 SKILL.md 行数

**【级别】** 要求

**【描述】**

整个 `SKILL.md` 不大于 500 行。

#### G.BOD.06 明确辅助文件的读取条件

**【级别】** 要求

**【描述】**

`SKILL.md` 正文直接说明在什么条件下读取哪份 `references/` 文件或执行哪个脚本；不得要求 Agent 启动时加载整个资源目录。参考文件的引用层级按 `G.RES.02` 执行。

#### G.BOD.07 `SKILL.md` 正文不得包含时间敏感、版本敏感或其他易过期信息

**【级别】** 要求

**【描述】**

`SKILL.md` 正文和 `references/` 中用于长期维护的说明，不得直接写入固定日期、固定版本号、临时版本状态、配额、镜像地址、人员名单等易过期信息。任务执行确需使用版本、地址、配额或责任人信息时，从仓库正式配置、依赖文件或维护清单中读取，并引用对应路径。

用于说明兼容范围、锁定依赖或复现实测结果的版本信息，应记录在对应配置或证据中，不属于本条禁止范围。

## 6 参考资料、脚本、资源和依赖

### 6.1 `references/`

#### G.RES.01 `references/` 只放按条件读取的详细资料

**【级别】** 要求

**【描述】**

`references/` 只用于保存 Agent 在特定条件下才需要读取的领域知识、规则和说明文档。每个参考文件只处理一个主题，文件名说明内容。

Agent 需要理解的规则不得放入 `assets/`；能够在 `SKILL.md` 中用几句话说清的内容也不应另建参考文件。

#### G.RES.02 `SKILL.md` 必须直接引用必需的参考文件

**【级别】** 要求

**【描述】**

`SKILL.md` 直接引用执行任务所必需的参考文件。非必需的扩展资料可以通过一级索引继续导航，但不得把关键规则只放在二级或更深层引用中。较长的参考文件应提供目录或检索关键词。

#### G.RES.03 引用正式资料，不维护重复副本

**【级别】** 要求

**【描述】**

仓库已有编码规范、设计说明、接口文档或模板时，在 Skill 中引用正式文件，不得复制正式文件内容。确需保存外部离线副本时，记录来源、许可证、版本或 commit、同步日期和更新责任。

### 6.2 `scripts/`

#### G.SCR.01 只为确定性和重复性操作增加脚本

**【级别】** 建议

**【描述】**

操作需要稳定结果、重复执行、容易人工出错或适合机器校验时，应优先使用脚本。清晰指令已经能稳定完成的一次性简单操作，不应额外增加脚本。

#### G.SCR.02 脚本必须有明确执行入口并声明依赖

**【级别】** 要求

**【描述】**

供执行的脚本能够脱离 Agent 独立运行；脚本所需代码、配置和依赖随 Skill 提供或明确声明。脚本自包含，或在文件头、依赖文件或 `SKILL.md` 正文中声明运行环境、外部依赖和已验证版本。

脚本存在明确依赖时，写清依赖名称、用途、版本要求和已验证版本。需要完全复现的执行环境使用精确版本；允许版本范围时，同时记录已验证版本。

#### G.SCR.03 脚本参数和运行入口必须清楚

**【级别】** 要求

**【描述】**

脚本文件名说明职责并遵守所在仓库的命名规则，禁止使用 `script1.py`、`utils.py` 等无法判断用途的名称。参数名称应稳定、语义明确。`SKILL.md` 正文说明执行入口、必需参数和输出用途。

应优先复用仓库已有环境变量。新增环境变量或开关时，说明含义、取值范围和默认行为。

#### G.SCR.04 脚本不得硬编码私有环境或直接执行远端内容

**【级别】** 要求

**【描述】**

路径通过 Skill 根相对路径、参数或已声明环境变量传入，不硬编码个人目录、HOME、安装目录或平台 Skill 目录。脚本不得包含密钥、令牌、个人地址或无关内部服务地址；不得使用 `curl | bash`、`iwr | iex` 等方式直接执行未审查的远端内容。

#### G.SCR.05 脚本必须有测试和使用说明

**【级别】** 要求

**【描述】**

为脚本提供对应测试，具体覆盖项按 `G.EVL.02` 执行。评审材料提供脚本的真实运行结果，并说明调用场景、输入和输出。

新增脚本时，遵守所在仓库的版权头和许可证规则；改编第三方代码时，保留来源和上游版权。

### 6.3 `assets/`

#### G.RES.04 `assets/` 只保存输出所需的静态资源

**【级别】** 要求

**【描述】**

`assets/` 只保存生成输出时直接复制或加工的静态资源，例如模板、代码骨架、图标和字体。Agent 需要读取和理解的规则及说明文档放入 `references/`，不得放入 `assets/`。

不得在 `assets/` 中提交临时文件、构建产物和未审查的可执行二进制。任务必需的静态二进制模板可以提交，提交前检查其来源、许可证、大小和安全性。

## 7 信息来源和维护

### 7.1 信息来源

#### G.SRC.01 Skill 必须声明任务所依赖的信息来源

**【级别】** 要求

**【描述】**

`SKILL.md` 正文说明完成任务所依赖的仓库规范、代码、测试、构建文件、正式文档或其他资料。组件规范定义组件特有的信息来源及其优先级。

### 7.2 外部资料和知识维护

#### G.SRC.02 每项领域知识只维护一个正式来源

**【级别】** 要求

**【描述】**

为长期使用的领域规则指定唯一正式维护位置和责任人，并在 Skill 中引用该位置，不得在多个 Skill 中分别维护相同内容。来源失效、API 变化或目录调整时，更新引用和兼容性测试。无法继续维护该来源时，停止引用；无法找到替代来源时，应停用相关 Skill。

## 8 安全、权限和数据

### 8.1 最小权限和任务范围

#### G.SEC.01 默认使用完成任务所需的最小权限

**【级别】** 要求

**【描述】**

知识查询、架构分析、诊断和代码检视类 Skill 在 `SKILL.md` 正文中将默认操作范围限定为只读。修改类 Skill 在 `SKILL.md` 正文中将可写范围限定为用户请求涉及的仓内文件，并明确完成任务所需的最小权限。

### 8.2 高风险操作

#### G.SEC.02 高风险 Skill 必须设置运行时授权检查点

**【级别】** 要求

**【描述】**

涉及远端写入、安装软件或依赖、修改系统配置、管理员操作、删除、覆盖、移动文件或其他难以恢复操作的 Skill，在 `SKILL.md` 正文中标明高风险步骤并设置明确的运行时授权检查点。

`SKILL.md` 正文规定：执行高风险步骤前，检查用户授权是否覆盖操作目标、范围和影响；执行完成后，核对实际结果。不得将命令参数或脚本确认选项定义为用户授权。

### 8.3 敏感信息

#### G.SEC.03 密钥和敏感信息不得写入 Skill、仓库和输出

**【级别】** 要求

**【描述】**

不得将 Token、密码、证书私钥和其他敏感信息写入 frontmatter、`SKILL.md` 正文、脚本、评测样例、仓库文件或开发过程产生的提示内容、日志、报告和非受控临时文件。Skill 确需使用敏感信息时，`SKILL.md` 正文或脚本规定从受控密钥存储或受控输入读取，并对输出进行脱敏。

### 8.4 工作区和内容限制

#### G.SEC.04 临时产物不得污染 Skill 目录

**【级别】** 要求

**【描述】**

会产生临时文件、外部仓库、报告或构建结果的 Skill，在 `SKILL.md` 正文或脚本中规定将这些内容写入仓库约定目录或临时目录，不得写入 Skill 源目录；任务完成时，说明新增、修改、保留和未清理的文件。Skill 交付物不得依赖开发者机器上的全局文件才能运行。

#### G.SEC.05 Skill 不得改变用户默认行为

**【级别】** 要求

**【描述】**

`SKILL.md` 正文和脚本不得要求 Agent 在未经授权的情况下启用第三方插件、修改 Agent 默认配置或改变用户环境的默认行为。

## 9 评测和测试

### 9.1 评测准备和用例

#### G.EVL.01 至少提供一个正向和一个负向评测用例

**【级别】** 要求

**【描述】**

新增 Skill 或修改影响 Skill 行为的内容时，创建 `evals/`，至少提供 1 个正向用例和 1 个负向用例，并提供对应验证结果。正向用例验证 Skill 在适用任务中可以正常使用；负向用例验证 Skill 不会处理不属于自身范围的请求。组件规范可以根据组件风险规定更多用例。

### 9.2 脚本用例

#### G.EVL.02 脚本用例覆盖接口和副作用

**【级别】** 要求

**【描述】**

新增脚本或修改脚本的输入、输出时，至少提供 1 个正常输入用例和 1 个异常输入用例，并附对应验证结果。按 `G.SCR.05` 提供真实运行结果和使用说明。

## 10 评审和发布

### 10.1 开发流程

#### G.REL.01 按评测先行的顺序开发 Skill

**【级别】** 建议

**【描述】**

应按以下顺序开发 Skill：记录真实问题，确定边界与权限，先编写最低评测用例，再编写 `description`、`SKILL.md` 正文和资源。完成适用检查和评测后，再提交评审。

### 10.2 变更回归

#### G.REL.02 变更后执行受影响回归

**【级别】** 要求

**【描述】**

修改 `description`、权限边界、脚本副作用或核心流程时，运行受影响范围内的完整回归。只修改措辞时，也要判断是否改变调用、术语或完成标准，并执行相应用例。增删 Skill 或修改 Skill 名称后，还要按 `G.STR.07` 检查全部引用。

### 10.3 发布和安装

#### G.REL.03 发布内容只包含运行、维护和验证所需文件

**【级别】** 要求

**【描述】**

Skill 发布包只能包含 Skill 运行、维护和验证所需的文件，包括 `SKILL.md`、实际使用的脚本、参考资料、静态资源、平台适配文件和评测文件，并符合 `G.STR.03` 定义的目录结构。按 `G.STR.04`、`G.STR.06` 和 `G.RES.04` 检查无关文件，按 `G.SCR.05`、`G.RES.03` 和 `G.RES.04` 检查许可证和第三方来源。

#### G.REL.04 安装后验证发现和调用

**【级别】** 要求

**【描述】**

完成安装或同步后，验证目标 Agent 能发现 Skill、解析 frontmatter、正确调用并访问所需资源。执行跨仓安装时，记录上游版本和校验值。

## 11 维护、版本和停用

### 11.1 版本和兼容性

#### G.MNT.01 版本标识按发布需要使用

**【级别】** 建议

**【描述】**

公共规范不要求每个 Skill 具有独立版本号。需要独立发布、跨仓安装或管理兼容性时，可以使用字符串版本、tag 或 commit 标识版本。

#### G.MNT.02 兼容性说明必须真实且可验证

**【级别】** 要求

**【描述】**

兼容性说明只能记录会影响运行且已经验证的环境要求。支持范围变化时，同步更新兼容性说明、`SKILL.md` 正文中的已知限制、依赖版本和跨平台测试。不得将未验证的平台写成已支持。

### 11.2 停用和合并

#### G.MNT.03 符合条件时停用或合并 Skill

**【级别】** 建议

**【描述】**

发现以下情况时，应评估停用或合并 Skill：

- 能力已被模型、系统提示、`AGENTS.md` 或统一工具稳定覆盖；
- 长期没有真实使用且加载成本较高；
- 与其他 Skill 重复，无法建立清晰边界；
- 领域知识已经过时且没有维护人；
- 安全或维护成本超过实际收益。

停用 Skill 前，应通过回归确认替代方式能够稳定覆盖原有任务。

## 附录 A 最小 Skill 示例

### A.1 最小目录

```text
.agents/skills/report-reviewer/
├── SKILL.md
├── references/
│   └── review-checks.md
└── evals/
    └── routing-cases.yaml
```

只创建实际需要的目录。上例没有脚本和输出资源，因此不创建 `scripts/` 和 `assets/`。

### A.2 最小 SKILL.md

```markdown
---
name: report-reviewer
description: 审查技术报告的事实依据、结构和结论，输出带原文位置的检查结果。当用户提交报告或要求内容审查时使用；不直接改写报告，也不负责生成新报告。
---

# 技术报告审查

## 输入与前置条件

- 目标报告；
- 当前仓库适用的写作和事实来源要求；
- 预期读者。无法从材料确认且会影响结论时，再询问用户。

## 工作流程

1. 读取目标报告，确定事实、推断、结论和建议的范围。
2. 报告包含技术结论时，读取 `references/review-checks.md`。
3. 按组件规范选择适用检查项；每项记录路径、符号、结论和未验证原因。
4. 保持只读，不修改文件。需要修复时先向用户说明范围并取得明确要求。

## 验收标准

- 每个问题都有可复查证据；
- 事实、推断和未验证项分开；
- 不遗漏适用的事实和结构检查；
- 没有未授权写操作。

## 已知限制

- 缺少原始数据时，不宣称报告中的数值已经验证。
```

最小示例只演示结构，不代替组件业务规则。实际 Skill 不需要为不适用内容创建空章节。
