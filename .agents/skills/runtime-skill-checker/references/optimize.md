# 优化模式

## 进入条件

- 审查已经完成且 `review-result.yaml` 通过最终校验。
- 审查模式最后已经取得用户对具体编号的明确授权。
- 报告路径和目标 Skill 路径已经确定。

没有合格的审查结果和有效授权时停止。不要脱离用户指定的问题项扩展优化目标。

## 执行流程

### 1. 建立授权集合

读取用户明确授权的 `Fail-*` 或 `Suggest-*` 编号，写入 `optimization.requested_failure_ids`。

逐项确认问题项存在且结构完整。未获授权的问题项保持不变。

### 2. 验证问题项

重新读取问题项指向的位置和必要上下文，验证证据、问题、影响和建议是否成立。不执行审查与优化之间的版本或哈希一致性检查。

- 原意见错误：`rejected`，记录理由，不修改代码。
- 缺少业务信息、环境或需要越界：`blocked`，记录所需条件。
- 仍成立且可在允许范围内处理：进入修改。

### 3. 检查修改边界

允许修改的文件必须同时满足：

- 位于目标 Skill 根目录内；
- 与该问题项直接相关；
- 用户授权覆盖该问题项；

不满足时标记为已阻塞。

### 4. 实施和验证

按最小范围修改。运行问题项中适用、安全且环境具备的验证项。验证失败时不要伪造通过；根据实际情况回退不完整改动，或把该问题项标记为失败或已阻塞，并说明当前状态。

检查最终修改差异，确认没有未授权文件和无关修改。随后验证已处理问题和受影响规则的状态。

目标 `SKILL.md` 正文用任务和触发条件说明职责边界，不出现其他 Skill 的名称。

### 5. 更新同一事实源

每个获授权问题项增加 `resolution`：

- 已修复（`fixed`）：问题已消除且检查全部通过；
- 失败（`failed`）：问题没有完全消除，或检查没有全部通过；
- 已驳回（`rejected`）：复核后原意见不成立；
- 已阻塞（`blocked`）：检查器不应或不能继续执行。

记录修改文件、逐项验证结果、剩余风险和原因。已驳回的修改文件必须为空。失败结果必须明确剩余风险和未完成原因，不得使用“部分修复”状态。

重新验证受影响规则，将复核证据和处理结果写入对应问题项的 `resolution`。保留原规则判定、审查证据和问题编号，不改写原审查结果。不要创建第二份结果文件，不要添加代码快照、提交、差异摘要或文件哈希字段。

### 6. 完成检查

运行统一入口脚本校验优化模式要求并重新渲染同一份 `review-report.md`。报告仍只列适用规则，并按是否存在 `Fail-*` 计算总体结论；保留的原问题编号仍计入该结论，处理进度单独展示在优化结果中。向用户说明各问题项的处理结果、验证失败和人工动作；不要输出工具调用日志。
