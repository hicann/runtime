# 审查模式

## 目标

依据 Runtime 正式规范 `docs/zh/guidelines/agent-skill-guidelines.md` 审查目标 Skill，形成可复查的 YAML 结果和 Markdown 报告。只检查当前 Skill 交付物和本次审查上下文能够证明的规范项，不把创建历史、发布流程或维护决策作为默认检测项。工具可按环境调整，但取证范围、判定规则和完成条件必须完整执行。

## 审查流程

### 1. 确定输入正确

确认目标 Skill、Runtime 正式规范和报告输出目录。需要核验同仓库资源时，从目标路径定位 Runtime 仓库根目录，但不把仓库根目录写入结果文件。

同时确认：

- 目标是包含 `SKILL.md` 的 Skill 目录；
- 报告目录位于目标 Skill 之外；
- 读取 Runtime 仓库根目录下的正式规范 `docs/zh/guidelines/agent-skill-guidelines.md`。

`review-result.yaml` 只保存目标 Skill 的实际路径，不保存规范路径、摘要、规则总数或仓库根路径，也不记录工具调用信息。

### 2. 建立规则矩阵

运行统一入口脚本，从正式规范动态提取全部 `G.<类别>.<序号>` 规则、标题、级别和原文行号。不得手工维护规则清单。

提取结果必须满足：规则 ID 唯一；每条规则都有标题和“要求”或“建议”级别。否则停止审查。准备脚本只把默认审查规则的 ID 和可填写判定字段写入 YAML，并将状态初始化为 `pending`；标题、级别和行号由脚本动态读取。

对于 `agent-skill-guidelines.md` 按以下顺序筛选规则：

1. 准备阶段固定排除只适用于创建、评测、评审发布或维护决策的规则这些规则不进入本次审查的 rules，也不参与汇总和评分。
   - 第 2 章 Skill 创建条件和任务边界
   - 第 9 章评测和测试
   - 第 10 章评审和发布
   - 第 11 章维护、版本和停用
2. 对其余规则读取规则前提和当前目标特征，仅保留当前审查适用的规则。
3. 完成取证后，对保留规则逐条判定为 `pass` 或 `fail`。证据不足不能作为移除适用规则的理由。

审查者只需从 `rules` 中继续移除其他不适用规则，不输出不适用项。汇总和评分由脚本根据保留规则及当前规范动态计算。

### 3. 获取证据

先完整枚举目标目录（含隐藏文件），记录任务相关目录和文件的路径、大小、入口及资源类别，再按规则需要读取内容。不得因为文件是文本格式就读取全部内容。

默认跳过 `.git/`、`.hg/`、`.svn/`、`.venv/`、`venv/`、`node_modules/`、`__pycache__/`、`.pytest_cache/`、`.mypy_cache/`、`.ruff_cache/`、`build/`、`dist/`、`target/` 等版本控制数据、依赖目录、缓存和构建产物。目标文件明确引用其中内容，或某条适用规则需要检查其存在性时，只读取完成该检查所需的最小范围。二进制文件和无关大文件只记录类型、位置及任务相关元数据，不执行或全文读取。

至少检查：

- `SKILL.md` 的 frontmatter 和正文；
- `references/`、`scripts/`、`assets/`、`evals/`、`agents/` 的存在性和用途；
- 交付范围内的临时文件、缓存、占位符、额外说明文件和空目录；
- 相对链接、依赖声明、脚本入口、测试及验证结果；
- 敏感信息、高风险动作、写入范围和报告位置。

只把事实写入对应规则的 `evidence`，不创建工具调用清单。

再从 Runtime 仓库验证目标实际引用的文档、组件规范、相邻 Skill、索引、依赖和平台适配文件。只检查适用规则所需的内容，以及可能接收相同请求且职责相邻的 Skill，不对仓库执行无目的全文读取。

相邻 Skill 仅用于比较任务范围和调用条件，不得因目标正文没有列出其名称而判定失败。规范中的职责分工按任务条件理解，不要求在正文点名。生成正文修改建议时，用任务、输入、输出和触发条件表达边界，保留必要的判断和停止条件，不得引入其他 Skill 的具体名称、转交指令或作为名称替代的跨 Skill 路径。此项是检查器的执行约束，不改写规范原文、不新增规则编号，也不将其他 Skill 名称单独作为规范失败项；当前 Skill 自身名称、通用术语和本 Skill 的任务资源引用不据此判错。

### 4. 对领域知识正式来源的说明

- `.agents/skills/<skill-name>/` 是同一仓库内 Skill 的正式维护位置。
- 目标位于 `.claude/skills/<skill-name>/` 或其他平台目录时，在仓库根目录查找同名的 `.agents/skills/<skill-name>/`。正式版本缺失时判定为 `fail`。
- 平台目录应为经过验证的链接、由正式版本生成的副本，或仅保存平台差异的适配层。比较两侧共有的 `SKILL.md`、`references/`、`scripts/`、`assets/` 和 `evals/` 文件；同一路径的共享文件内容必须一致。
- 平台专属配置可以不同。平台目录不得复制完整正文或领域知识后独立修改；共享文件内容分叉，或两个目录分别维护同一份领域知识时，判定为 `fail`。
- 目标本身位于 `.agents/skills/<skill-name>/` 时，将其作为正式版本检查，不要求与自身重复比较。目标位于其他位置时，仍按同名规则查找 `.agents/skills/<skill-name>/`。

验证目标前评估副作用：结构解析、语法编译和只读命令可以执行，但缓存和中间文件必须写入临时目录；不得自动执行未知脚本、联网、安装依赖、远端写入或会修改目标的测试。无法安全核验的事项按“逐条判定”处理，并记录检查范围、缺失材料及补充方式。

## 逐条判定

仅对适用规则逐条判定，YAML 内部状态如下：

- `pass`：证据足以证明满足口径；
- `fail`：有证据确认适用要求未满足，且能说明具体影响和维护者可执行的处理；记录事实、影响和处理依据；

最终判定仅使用 `pass` 或 `fail`，未完成判定时允许保留 `pending`。不适用规则从 `rules` 中移除，不得因证据不足移除适用规则。`pass` 和 `fail` 都必须附证据。证据不足时继续核验；关键要求仍无法核验时，将 `review.status` 标为 `blocked`，在 `review.blocking_reason` 记录原因，保留未判定规则的 `pending`，不输出审查完成结论。问题编号前缀决定总体结论：`Fail-*` 导致不通过，`Suggest-*` 不改变通过结论。报告状态列输出 `pass` 或关联的问题编号。

## 问题项与评分

生成问题项前，先核对相关上下文，确认已有可定位证据、当前任务中的具体影响，以及维护者可执行的处理和预期收益。风险判断须能从已有输入、调用方式或运行条件中得到支持；不得自行假设前提。

问题项可关联多条同级别规则，但不得混合要求与建议或合并无关问题。编号分别连续使用 `Fail-001`、`Suggest-001`。位置指向最小可检查范围，建议必须能直接指导优化。

每个问题项按 `references/result-schema.md` 第 4 节填写。

diff 以 `@@ 相对路径:行号` 开始，行号指向该块第一处修改，不得用章节标题或自然语言位置代替。每块只包含一个连续修改，至少有一行以 `+` 或 `-` 开头：新增用 `+`，替换用连续的 `-` 和 `+`，删除用 `-`；不连续的位置分别另起修改块。块内可提供以一个空格开头的简短上下文，上下文可选、不作为合法性门禁。diff 应基于实际文件内容，只保留与当前问题直接相关的最小内容。 建议修改后的 `SKILL.md` 正文须遵守入口文档的职责边界表述要求；当前修改块不得引入或保留其他 Skill 的具体名称，也不得用转交指令或跨 Skill 路径替代条件说明，不得为此扩展无关修改范围。输出前比较修改前后的文本，仅保留存在实际差异的修改块。

证据不足的处理按“逐条判定”执行，不把未核实的推测写入问题项。

按“要求=5、建议=1”计分：通过获得对应权重，失败不得分，不适用不计入分母。报告展示适用规则统计、百分制评分及加权分子/分母。存在 `Fail-*` 则整体不通过，否则通过；`Suggest-*` 不影响整体通过。评分和总体结论由脚本计算，未完成审查不输出总体结论。

## 完成与优化

完成判定后运行统一入口脚本。只有最终校验成功时才由 YAML 覆盖 Markdown。确认报告目录只有md和yaml文件，且目标 Skill 未被修改。

- 无问题项：保持审查模式，优化状态为未开始。
- 存在 `Fail-*` 或 `Suggest-*`：保持审查模式，优化状态为等待确认，授权列表为空，并列出编号、问题和建议。

只有用户明确给出问题编号后才能优化。届时将编号写入 `optimization.requested_failure_ids`，模式切换为 `optimize`，再读取 `references/optimize.md`。用户暂不优化时保持目标 Skill 不变并结束。询问期间不生成第三份报告、不记录工具调用日志，也不改变既有判定。
